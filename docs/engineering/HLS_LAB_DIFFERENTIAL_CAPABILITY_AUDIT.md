# HLS Laboratory — differential capability audit

**Audit date:** 2026-10-17
**Repository revision inspected:** 8d16f90, branch feature/hls-laboratory-v1. The audit was read-only with respect to models, protocols, and results.
**Decision:** **GO for bounded validation using existing components; HOLD on new adaptive infrastructure pending that validation.** This is not authorization to run a campaign.

## 1. Executive diagnosis

The repository already implements several distinct forms of adaptive behavior. Current evidence does not justify the general conclusion that new adaptive capabilities must first be built. The nearer-term gap is primarily correct configuration, discrimination, and validation of capabilities already present. This is not a claim that all adaptive mechanisms from the literature exist in HLS, or that current policies are generally effective.

The distinctions are important:

* **Changing demand exists:** C5 provides stationary IID, time-indexed nonstationary, and first-order Markov task processes; the N×K environment freezes a generated exogenous trajectory before policy execution. Tests cover these process contracts. This is not itself adaptive decision-making.
* **State-dependent decisions exist:** P0/P1/P2 choose each period from a declared decision view; Nembhard ORACLE uses current true productivity; Nembhard ADAPTIVE uses its estimates and exploration; the contextual quality–cost router updates selected-candidate predictors from feedback. Their estimands and information differ. P2's adaptive memory is teaching-efficacy memory, not generic task-allocation learning.
* **Experience-dependent states exist:** MIS-v2 evolves normalized competence; Nembhard Direct evolves separate experience and productivity states. These are different laws. G2/MIS theory and earlier HLS studies already establish conditional intertemporal development value; that result should not be rediscovered with an uncoupled toy model.
* **E1 and E2 do not invalidate those capabilities.** E1's task-conditioned FIXED dispatch was aligned to the constructed productivity roles, while ADAPTIVE estimated a moving productivity signal using a historical mean. In mixed/specialist profiles FIXED and immediate ORACLE almost always selected the same action; key outcomes had little room to distinguish them. E2.0/E2.1 isolate separable rewards where increasing productivity makes cumulative reward discretely convex. For each independent task type an endpoint allocation to one agent is at least as good as splitting; BEST-STATIC was globally optimized. The model excludes the coupling needed for reassignment to help. E2.1 is a valid negative control for its assumptions, not a verdict on the broader laboratory. The repository also contains earlier HLS dynamic characterization and stress-pilot results: these exercise a visible demand-orientation switch, competence-information conditions, MIS-v2 learning rates and policy differences in the legacy dynamic path. They are bounded and not equivalent to N×K/Nembhard allocation, but they refute the stronger claim that HLS has never demonstrated a changing-demand adaptive scenario.

**Operational conclusion:** configure existing frozen-demand, N×K, Nembhard, and dynamic-reference components for small validation. Test both static null cases and already-established coupled/intertemporal positive fixtures, and verify that a supported nonstationary trajectory changes the selected action when the task/regime changes the relevant ranking. Do not start another E2.x experiment, weaken BEST-STATIC, or add a policy to manufacture a positive result.

Evidence labels:

* **Implementation fact:** directly checked source behavior and declared inputs/outputs.
* **Test evidence:** a software contract/regression is exercised; not by itself scientific validation.
* **Experimental evidence:** a recorded execution under an explicit protocol; conclusions remain within its model and conditions.
* **Analytical result:** follows from the stated mathematical model; scope remains limited to that model.
* **Interpretation:** methodological conclusion, not a source-code or result fact.

The worktree contained unrelated pre-existing modified and untracked files. They were preserved. No test suite, campaign, or simulation was run for this report.

### Adaptive concepts are not synonyms

| Concept | Existing instance | Meaning / non-implication |
|---|---|---|
| Dynamic environment | C5 and N×K demand generator | Exogenous task/probability/state changes; does not imply regime detection or an effective response. |
| State-dependent decision | P0/P1/P2 and Nembhard routers | Decision recomputed from current task/view; does not imply parameter learning or future planning. |
| Online estimation | Skill posterior, Nembhard means, contextual ridge | Estimate a named latent quantity from observations; does not imply correct model, identification, or improved outcomes. |
| Online policy learning | Nembhard ADAPTIVE and contextual router | Feedback can change later decisions; not learning the true curve or universal generalization. |
| Experience-dependent development | MIS-v2 competence; Nembhard D/productivity | Work changes a physical state; does not imply a policy exploits it optimally. |
| Adaptive coordination | Per-period allocation/teaching rules | Decisions vary with views/memory; not a universal meta-controller or proof of superiority. |

## 4. Existing adaptive capability: differential source findings

**Demand.** C5 implements stationary IID draws, index/time-specific distributions, and first-order transitions from the previous task (src/hls/synthetic/c5.py). N×K wraps finite problem catalogues and regime metadata in DemandRegimeNK, ExogenousEnvironmentConfigNK and EnvironmentTrajectoryNK; generate_environment_trajectory_nk freezes the path before policy execution (src/hls/hls_lab_nk_environment.py). Tests in tests/synthetic/test_c5_dynamic_demand.py and tests/test_hls_lab_nk_environment.py cover transition, regime-change, replay and independence contracts. The N×K runner-integration test crosses P0/P1/P2, MIS/teaching and perfect/imperfect information, but its generated demand fixture is stationary; the N×K nonstationary/Markov generator is tested separately. The legacy dynamic pilot fills part of the behavioral evidence gap: HLS_DYNAMIC_STRESS_PILOT records a 448-run study with a four-problem requirement-orientation switch, and HLS_DYNAMIC_LAB_CHARACTERIZATION records a 256-run stationary/switching study. For example, switching/heterogeneous H=3 in the stress pilot reports second-half success 1.0 for Greedy off and slow/fast learning arms, 0.96 for updated partial estimates, and 0.40 for DISCOVER; this is an outcome of differing objective/information rules, not a universal ranking. The legacy pilot plus N×K generator tests demonstrate that the repository has adaptive scenarios, but do not constitute N×K generated-nonstationary policy validation.

**P0/P1/P2.** src/hls/hls_lab_nk_policies.py defines a per-period choose(view,memory,parameters) contract. P0 ranks production actions by functional success, normalized deficit, margin and effort. P1 attempts its configured directed teaching relation and falls back to production. P2 uses formative efficacy memory; it does not learn a generic task-allocation model or optimize future return. tests/test_hls_lab_nk_policies.py pins policy choices and legacy behavior.

**Legacy dynamic decision mechanisms.** The older v1 path in src/hls/hls_lab_v1.py has FixedRouting, GreedyAdaptive and ExploreThenGreedy over its fixed 3×2/64-action domain. GreedyAdaptive responds to current requirements and the estimate in its DecisionView but has an immutable policy state: state response, not policy learning. ExploreThenGreedy has a persistent OrganizationState table; it first explores legal actions for a problem context, then uses observed average binary success. That is online policy learning in a narrow tabular, context-keyed form. The dynamic pilot report shows its comparison against updates-off is confounded: with empty memory, OFF repeats the first action, while ON both explores and updates from outcomes. tests/test_hls_lab_v1.py and tests/test_hls_lab_dynamic.py cover these code paths.

**Belief-state planning.** src/hls/hls_lab_dynamic.py::DiscoverBeliefPolicy calls the existing DISCOVER unknown_policy_value finite-horizon solver. run_belief_sequence maintains a belief over the hidden CES environment type, resets that belief per problem, and separately updates actual/estimated competence as configured. Its planning horizon is real, but the solver assumes fixed capabilities within its recursion; MIS changes between decisions and is not forecast in that recursion. This is model-based finite-horizon planning under payoff-type uncertainty, not an online learned allocation rule or general N×K planner. The dynamic characterization/stress-pilot documents explicitly distinguish the solver's CES objective from functional success.

**Competence estimation.** src/hls/hls_lab_dynamic.py::update_skill_posterior applies a bounded-grid Bayesian update under observation y = effort × actual competence + Normal(0, σ²); predict_skill_posterior_after_mis propagates through MIS-v2. src/hls/hls_lab_nk_estimation.py wraps it for N×K. In imperfect mode, actual competence drives physical production and estimates are exposed to decisions through src/hls/hls_lab_nk_execution.py. It is not an estimator of Nembhard productivity, model quality, money, latency or task difficulty.

**Nembhard productivity route.** src/hls/hls_lab_nk_nembhard.py computes start-of-period productivity from true D and separate (k,p,r), then advances D after work. NembhardOracleRouterNK receives current true state/parameters and ranks current-period actions. NembhardAdaptiveRouterNK receives no true productivity or (k,p,r); it updates a per-cell running mean from selected-work observations and uses optional epsilon exploration. Its mean can lag a productivity signal that rises with experience; it does not fit the curve parameters. Tests include information boundaries, update order, exploration/replay and divergence from ORACLE (tests/test_hls_lab_nk_nembhard_adaptive.py; tests/test_hls_lab_nk_nembhard_oracle.py). This is genuine online adaptive allocation in a narrow sense, but not an online planner.

**Other routing.** The contextual quality–cost router is a separate selected-candidate feedback learner. Campaign 3 META-VOC is yet another sequential FAST/DEEP selector with a frozen synthetic-domain result. Neither is an N×K allocator using C5 demand, nor a reproduction of MixLLM or System-1.x. The legacy path also includes DISCOVER-backed finite-horizon belief planning: DiscoverBeliefPolicy delegates to unknown_policy_value and run_belief_sequence resets hidden CES-type belief at problem boundaries. Its recursion holds competence fixed inside the planning horizon even though MIS-v2 transitions occur between decisions; H=3 comparisons also change planning opportunities and learning exposure. It is not a general N×K learned allocator.

## 7. HLS-E2.0 and E2.1 diagnosis

### E2.0

experiments/hls_e2/hls_e2_0.py is a self-contained standard-library model with two agents, one task/skill, one-unit choices, the Direct curve, work-based experience and exact memoized optimization. It compares the optimizer with greedy and a fixed rule choosing the greater initial productivity over 1,000 seeded parameter draws at each horizon. The saved result reports OPT beats that baseline in 157/1,000 cases at T=20, 205/1,000 at T=60, and 234/1,000 at T=120. These are not dynamic-versus-best-static comparisons: the fixed baseline is not optimized over the full horizon. The structural result says a same-agent allocation attains an optimum in the one-skill uncoupled model; the sample counts measure DP gain over the initial-greedy/fixed rules. E2.0 has no task types, globally optimized task-conditioned static baseline, N×K runner, C5 process, observation/estimation, or policy integration.

### E2.1

experiments/hls_e2/hls_e2_1.py uses two agents, two independent skills/task types, one unit task per period, a single assigned agent and cellwise experience increment of one. Reward is current productivity before updating the same cell. There are no concurrent tasks, shared capacity across tasks, cross-skill production, functional complementarity, noisy information, uncertainty, exploration, teaching or MIS-v2. OPT-DYNAMIC knows the whole future sequence; BEST-STATIC enumerates all four task→agent maps and optimizes each on the same path/reward. This is an appropriately strong baseline for the question it asks.

The saved e2_1_results.json reports 33 deterministic cases, no dynamic-static gap above 1e-10, DP agreement with an independent exhaustive validator on small horizons, and reward/trajectory consistency. The protocol's mathematical deduction is valid within scope: for a task type with n occurrences, F_i(m)=Σ from j=0 to m−1 of P_i(D_i0+j) has nondecreasing increments because P is nondecreasing. Therefore F_0(m)+F_1(n−m) is convex over the integer split interval; a convex function on this interval attains a maximum at an endpoint. Independent skills decompose, so assigning each type to one agent is representable by BEST-STATIC. The observed stationary-per-type optima corroborate but do not prove the result.

**E2 validates:** the standalone Direct state/reward recurrence, DP vs exhaustive search, strong optimized static baseline, deterministic-case reproducibility and the endpoint result for the declared separable reward.

**E2 does not validate:** the N×K execution/environment path, P0/P1/P2, competence estimation, online learning, imperfect information, exploration, shared cross-task resource coupling, collective functional complementarity, or a general conclusion that dynamic allocation cannot help. The model is a useful negative control but a poor test of full-laboratory adaptive organizational capability.

## 10. Minimal corrective validation plan

These are proposals for validation only; no campaign is authorized. Passing means correct representation, trace and predeclared discrimination—not that ADAPTIVE wins. Reuse components; do not create new physics.

| **1. N×K generated nonstationary demand → policy execution contract** | Reuse the already-tested NonStationaryTaskDemand or MarkovTaskDemand fixture and the existing N×K runner; do not invent a process or problem catalogue. Cross it with an existing policy and paired frozen path. The current runner integration matrix uses a stationary generated-demand fixture, while nonstationary/Markov generation is tested separately. | Verify exact emitted regime/problem sequence, then that the runner receives that path unchanged, makes feasible decisions from the current authorized view, produces from actual state, and records transition order. V1 is the best first action because the existing code tests generation and runner integration but only combines them under a stationary generated-demand fixture; the missing evidence is a small wiring check of the already-supported nonstationary/Markov process, not new infrastructure or a new experiment scenario. The legacy dynamic pilot already demonstrates changing requirements in its separate 3×2 path. V2 prevents rediscovery of known dynamic-value results. V3 directly addresses E1 but should follow an ex-ante discrimination audit; do not repeat 1,016 episodes to obtain more of the same near-equivalent decisions.

## 11. Priorities, unresolved points, and recommendation

1. **First:** verify existing nonstationary/Markov N×K demand generation end-to-end with one existing runner fixture (high relevance, high reuse, low cost; no new demand model).
2. **Second:** preserve G2/MIS analytic positive and null fixtures as reference oracles (high diagnostic value, low–moderate cost).
3. **Third:** only then run a bounded, preflighted Nembhard policy comparison (direct relevance to E1; moderate effort).

Confirmed: dynamic processes and policy interfaces exist; E1's FIXED map is profile-aligned; observed FIXED/ORACLE overlap and outcome saturation are real; Nembhard ADAPTIVE averages a moving productivity signal; E2's independent-skill assumptions imply endpoint allocation and BEST-STATIC can represent it.

Unresolved: whether an already-supported N×K coupled configuration yields a robust dynamic allocation advantage; how much of E1's ADAPTIVE loss is due to estimation, exploration, information, or profile choice; generalization of the contextual router; and full external-paper reproducibility. These uncertainties do not justify immediate model expansion.

Residual risks include label inflation between dynamic demand and adaptive decision; mischaracterizing a profile-informed static reference; conflating ORACLE information with ADAPTIVE estimation/exploration; saturation of binary outcomes; and semantic drift between Nembhard productivity, Baccara queue welfare, MixLLM quality/cost, System-1.x search and HLS competence/CES. HLS_CURRENT_STATE.md also contains dated historical snapshots that say some now-implemented components were unsupported; use its consolidated current section and source/tests, not isolated old entries.

**Recommendation: GO** for bounded validation using existing components; **HOLD** on new adaptive mechanisms and on a large campaign until a discriminating configuration is predeclared and approved. The evidence points primarily to configuration/validation gaps, not absence of all adaptive capability. The laboratory does not yet implement every external mechanism, a universal adaptive allocator, or a scientifically validated general theory of adaptive organizations.

> **Central answer:** Primarily configure and validate correctly the dynamic and adaptive capabilities already implemented. Build new capabilities only if a specific requirement fails validation and its missing dependency is demonstrated from code, tests, and a scoped scientific question.
